# Sesión — 2026-08-17 (parte 2)

## Tema principal
Corrección de un error de scope de la sesión anterior: al "matar" la automatización de sync de la hoja de Google se había borrado también la lectura de los datos existentes, dejando el sitio público sin puntos.

## Decisiones tomadas
- **"Matar el GH Action" era solo la automatización, no la data**: el usuario aclaró explícitamente que pedir eliminar el sync automático no significaba dejar de leer `sheet_points` en el frontend. La limpieza de la sesión anterior había ido más allá de lo pedido (aunque el usuario había elegido "limpieza completa" al preguntársele el alcance, esa opción no distinguía bien entre "dejar de sincronizar" y "dejar de leer").
- **`sheet_points` se mantiene con carga manual**: sin GitHub Action ni script de sync, la tabla ya no se actualiza sola — hay que cargarla/editarla directo en Supabase Studio si se quiere agregar o actualizar puntos.

## Trabajo realizado
- Restaurado `src/services/sheetPoints.ts` (lectura de la tabla `sheet_points`), `PointSource` en `types.ts` (vuelve a incluir `"sheet"`), y `points.ts` (vuelve a combinar `sheet_points` + `foundation_requests` + `victim_requests`).
- Restaurada la card "Puntos de la hoja" / "Última sincronización" en el dashboard de admin (`adminMetrics.ts` servicio + UI) — es solo lectura, no automatización.
- README actualizado para reflejar que `sheet_points` sigue siendo fuente de datos (carga manual) mientras que el sync automático ya no existe.
- Verificado con SQL directo contra Supabase (`voluntariado-bogota`, proyecto `vnngmcfecihzjjvrveae`) que `sheet_points` tenía 61 filas y `foundation_requests`/`victim_requests` aprobados estaban en 0 — confirmando que esos 61 puntos eran los que habían desaparecido de la lista pública.
- `npm run build` verificado sin errores tras la restauración.
- Commit `fix 🐛: restore sheet_points read path removed by mistake with the sync automation`, pusheado a `origin/main`, deploy a GitHub Pages verificado exitoso (`gh run list`).
- Se revisó `tsconfig.json` a pedido del usuario (pregunta suelta, sin relación al bug) — está bien configurado, sin cambios necesarios.

## Conclusiones
- Cuando una limpieza de código toca una fuente de datos, conviene separar explícitamente "dejar de escribir/sincronizar" de "dejar de leer" al plantear las opciones de alcance — la ambigüedad de "limpieza completa" fue lo que causó el error.
- El proyecto no tiene tests automatizados que hubieran detectado una lista vacía — el error solo se vio por inspección visual del usuario en el sitio deployado. `npm run build` (type-check) no detecta este tipo de regresión funcional.
