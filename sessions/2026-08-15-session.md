# Sesión — 2026-08-15

## Tema principal
Construcción completa, de cero a producción, de una app de voluntariado/donaciones para Bogotá (`donaciones` / repo `JuanFeDS/voluntariado`), partiendo de una hoja de Google Sheets comunitaria; luego evaluación de una especificación funcional mucho más ambiciosa recibida por WhatsApp y creación de un plan de acción para cerrar la brecha.

## Decisiones tomadas
- **Fuente de datos**: CSV en vivo al inicio → migrado a Supabase porque Google Sheets empezó a devolver 429 (rate limit) bajo el volumen de pruebas/uso real.
- **Mapa/geocoding**: Leaflet + OpenStreetMap + Nominatim en vez de Google Maps/Geocoding — cero costo, cero API key, coherente con presupuesto $0 de causa benéfica.
- **Sync hoja→Supabase**: GitHub Action con cron cada 10 min (`sync-sheet.yml`), no script manual.
- **Moderación**: los dos formularios públicos (fundaciones, damnificados) insertan con `status='pendiente'`; revisión manual directa en Supabase Studio, sin panel de admin propio todavía.
- **Privacidad damnificados**: dirección exacta y teléfono nunca públicos — solo localidad aproximada, tipo de ayuda y urgencia vía la vista `victim_requests_public` (sin lat/lng, para no filtrar ubicación indirectamente).
- **Hosting**: GitHub Pages bajo el dominio personal existente del usuario (`juanfeds.com/voluntariado/`), confirmado explícitamente con el usuario tras detectar que heredaba el CNAME del user-page.
- **Diseño visual**: sistema "tablero de despacho" tipo triage — el color ES el sistema de estado (rojo/ámbar/verde), sin "azul de marca" separado. Tipografías: Big Shoulders Display + Public Sans + JetBrains Mono, self-hosted (sin depender de Google Fonts en runtime).
- **Commits**: convención `/make-commits` (tipo+emoji, atómicos, inglés).

## Trabajo realizado
- App completa Vite + TypeScript vanilla: `index.html` (mapa/lista), `fundacion.html`, `damnificado.html`, con filtros, toggle Lista/Mapa en mobile.
- Proyecto Supabase creado (`voluntariado-bogota`, São Paulo, tier free, ref `vnngmcfecihzjjvrveae`): tablas `sheet_points`, `foundation_requests`, `victim_requests` + vista `victim_requests_public`, RLS en las tres, verificado con pruebas reales vía `curl` (no solo lectura de código): auto-aprobación bloqueada, datos sensibles inaccesibles, límites de longitud rechazando payloads.
- Revisión de seguridad: encontrados y corregidos XSS sin escapar en popups del mapa, inyección de esquema `javascript:` en links, agregado honeypot anti-spam y `CHECK` de longitud en DB.
- Bugs de robustez encontrados y arreglados en el camino: ícono roto de Leaflet (`_getIconUrl` bug conocido con bundlers), `tsconfig` sin `noEmit` generando `.js` sueltos, `base` de Vite rompiendo el dev server, y el más sutil: el parseo del CSV asumía un offset fijo de filas de encabezado que se rompió cuando alguien editó la hoja (ahora busca la fila "LUGAR" por contenido, no por posición).
- GitHub Actions: `sync-sheet.yml` (cron) y `deploy-pages.yml` (deploy en cada push a main). Ambos verificados corriendo exitosamente end-to-end.
- Rediseño visual completo (paleta triage, tipografías self-hosted vía `.woff2` copiados directo — `@fontsource` vía import no resolvía en Rollup, se abandonó ese approach).
- Mejora de UX mobile: detectado que el mapa quedaba enterrado bajo la lista (encontrado con capturas reales del usuario) → toggle Lista/Mapa; luego botón "Ver en el mapa" en cada tarjeta + popup enriquecido que se abre automáticamente al llegar desde la lista.
- Verificación visual con Playwright headless (`chromium-cli` no estaba disponible) en todas las iteraciones de diseño — el usuario pidió explícitamente no usar la extensión de Chrome.
- Recibido `especificacion-funcional.html` (documento externo, mucho más grande: registro humanitario post-sismo con motor de elegibilidad geográfica, OTP, roles, índice de cobertura/equidad territorial). Se leyó completo y se generó `plan-de-accion.md` con el gap analysis fase por fase.

## Conclusiones
- La app actual cubre ~25-30% incluso de la Fase 1 de la especificación grande — el índice de cobertura/equidad (el núcleo real de esa spec) no existe en absoluto hoy.
- Varias de las decisiones abiertas de esa spec (entidad responsable, jurisdicción de hosting, aliados institucionales) son de negocio/legales, no de código — bloquean cualquier avance real hacia ese producto más grande.
- El pipeline completo (hoja → Supabase → app en producción) quedó verificado funcionando de punta a punta con datos reales (58 puntos sincronizados).
